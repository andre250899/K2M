## Bugs reais encontrados e corrigidos nesta sessão

1. **Scan de plugins derrubava o host inteiro (crash real, não só do teste).** `PluginHost::scanDefaultVst3Directory()` consultava a fábrica de **todo** plugin VST3 da pasta `C:\Program Files\Common Files\VST3\` **no mesmo processo** (via `format->findAllTypesForFile`), sem isolamento. Nesta máquina, `Addictive Keys.vst3` (XLN Audio, build antigo 1.6.3/2021) tem um bug interno real: sua própria camada "Cotton" não acha `luasystem,BaseSystem.lua` na instalação, loga o erro e desreferencia um ponteiro nulo dentro do próprio `GetPluginFactory` — derrubando (segfault) qualquer processo que meramente pergunte "quais plugins você tem" a esse binário, sem nunca instanciá-lo de verdade. Isso afetava tanto `GateATest.exe` quanto o **K2M.exe real** (mesmo caminho de código em `MainComponent::scanPlugins`), ou seja, o app travava sempre que escaneava plugins numa pasta com esse binário quebrado — um problema de robustez da Fase 0/1 que nunca tinha sido testado numa pasta VST3 com plugins de terceiros diversos.
   - **Fix implementado:** scan isolado por processo, usando o padrão oficial do próprio exemplo `AudioPluginHost` do JUCE (`juce::KnownPluginList::CustomScanner` + `juce::ChildProcessCoordinator`/`ChildProcessWorker` + `juce::PluginDirectoryScanner`). Novo módulo `Source/Plugin/PluginScanWorker.h/.cpp` implementa o par coordinator/worker; `PluginHost::scanSearchPath()` agora usa `PluginDirectoryScanner` com esse `CustomScanner` instalado, de forma que cada arquivo é consultado num **processo filho descartável** — se ele crashar, só o filho morre, o host segue para o próximo arquivo. Worker dedicado `K2M_ScanWorker.exe` (novo target CMake, console simples sem `JUCEApplication`, compilado para a mesma pasta do `K2M.exe` via `RUNTIME_OUTPUT_DIRECTORY "$<TARGET_FILE_DIR:K2M>"` + `add_dependencies`). `GateATest.exe`/`GateBFixtureTest.exe` também reconhecem modo worker (auto-relançamento de si mesmos como fallback, ver `PluginScanWorker::resolveScanWorkerExecutable`), e isso funciona perfeitamente estável neles.
   - **Ressalva importante:** esse isolamento por processo está **implementado e funcional**, mas **hoje só está ligado nos executáveis de teste em console** (`GateATest`, `GateBFixtureTest`). `PluginHost` ganhou um parâmetro `useIsolatedScanning` no construtor (default `true`); `K2M.exe` (GUI) passa `false` e usa scan simples em processo único — porque no meio da investigação do crash abaixo eu inicialmente (e incorretamente) atribuí o crash do K2M.exe ao isolamento por processo, revertendo-o antes de descobrir a causa real (item 2). **Vale reconsiderar religar `useIsolatedScanning=true` no K2M.exe** numa sessão futura, já que o isolamento em si não era o problema.
   - Também removidos dois caminhos de busca hardcoded (`C:\Users\VOXX-PC\Documents\Projetos\K2M\build` e uma entrada duplicada de `C:\Program Files\Common Files\VST3`) que eram resíduo de outra máquina de desenvolvimento (mesmo usuário do `install_tools.bat`).
   - Filtro adicional pragmático em `PluginHost.cpp` (`isKnownBadPluginFile`): pula `Addictive Keys.vst3` explicitamente antes mesmo de tentar escaneá-lo (nome hardcoded, ver comentário no código). Com o isolamento por processo isso já não seria estritamente necessário para não derrubar o host, mas evita o ruído de sempre lançar-e-matar um processo filho para esse binário especificamente quebrado.

2. **K2M.exe (GUI) crashava ~12-40s depois de abrir — causa raiz diferente do scan.** Depois de corrigir o item 1, o `K2M.exe` real continuava crashando pouco depois de abrir (violação de acesso dentro de `VCRUNTIME140.dll`, sempre no mesmo offset `0x1e6b0` — confirmado repetidamente via Visualizador de Eventos do Windows). Passei um tempo considerável investigando isso como se fosse um problema de threading no `ChildProcessCoordinator`/`AsyncUpdater` (tentei: relançar processo próprio vs. worker dedicado, scan na thread de mensagens vs. thread de background dedicada) — **nenhuma dessas variantes resolveu**, porque a causa real era outra: **`MainComponent::applyScanResults()` chamava `pluginSelector.setSelectedId(kontaktIndex + 1)` sem especificar `NotificationType`**, e o padrão do JUCE para isso é `sendNotificationAsync` — ou seja, terminar o scan disparava automaticamente `pluginSelector.onChange` → `loadSelectedPlugin()` → **instanciação de verdade do Kontakt** (não só a consulta de descrição feita durante o scan), silenciosamente, sem o usuário pedir. Essa instanciação automática é o que crashava.
   - **Fix:** `setSelectedId(..., juce::dontSendNotification)` nos dois lugares de `applyScanResults()` — o Kontakt continua pré-selecionado visualmente no dropdown, mas carregar de fato agora depende de uma ação do usuário (reabrir a seleção/trocar e escolher de novo, ou um clique futuro num botão "Carregar" dedicado — hoje o próprio `onChange` é o único gatilho de carregamento, então tecnicamente é preciso re-selecionar o item para carregá-lo).
   - Com esse fix, `K2M.exe` ficou estável por **3+ minutos** (antes: crash consistente em 12-40s) — grande melhora, mas...
   - **Pendência real, não resolvida:** numa sessão de teste, o app crashou de novo depois de ~3-4 minutos de uso ocioso, **mesma assinatura exata** (`VCRUNTIME140.dll`, mesmo offset). Não investigado a fundo por tempo — suspeitas não confirmadas: o timer de UI a 30Hz (`startTimerHz(30)` em `MainComponent`) ou o dispositivo de áudio WASAPI (`AudioEngine`). **`GateATest.exe`/`GateBFixtureTest.exe` nunca reproduziram esse crash em nenhuma execução** (são console simples, sem timer de UI nem device de áudio persistente), então a validação de Gate A/B deve continuar por eles, não deixando `K2M.exe` aberto por períodos longos até isso ser investigado.
   - Tentativas de capturar um dump/stack trace do crash (via `cdb.exe` do Windows SDK, via `FileSystemWatcher` do PowerShell na pasta `WER\Temp`) não tiveram sucesso — o arquivo `.mdmp` temporário do Windows Error Reporting é apagado rápido demais para conseguir copiá-lo a tempo com as abordagens tentadas. Não há dump salvo para análise offline ainda.

## Setup necessário para retomar em outra máquina

1. Clonar (se ainda não clonado) e/ou `git pull` no repo.
2. Submodule do JUCE: `git submodule update --init --recursive` (o build depende de `external/JUCE`, tag 8.0.12 fixada — não deixar mudar para `master`).
3. CMake: se não houver CMake standalone instalado, mas houver Visual Studio 2022, use o CMake embutido nele:
   `"C:\Program Files\Microsoft Visual Studio\2022\Community\Common7\IDE\CommonExtensions\Microsoft\CMake\CMake\bin"` (ajustar edição se não for Community) — adicionar ao PATH da sessão antes de rodar `cmake`.
4. `cmake -S . -B build -A x64` e `cmake --build build --config Release`. Isso agora também compila `K2M_ScanWorker.exe` (colocado automaticamente ao lado de `K2M.exe` via dependência do target `K2M`).
5. **`external/sfizz_render/` não é versionado** (binário de terceiros, .gitignore). Se quiser rerodar `SfzEngineValidationTest.exe`, baixar de novo:
   `https://github.com/sfztools/sfizz/releases/download/1.2.3/sfizz-1.2.3-win64.zip`, extrair `bin/Release/sfizz_render.exe` e `bin/Release/sfizz.dll` para `external/sfizz_render/`. Sem esses arquivos o teste avisa e sai com código 0 (não bloqueia o resto do build).
6. Kontakt precisa estar instalado e autorizado via Native Access; o scan do `PluginHost` já cobre `C:\Program Files\Common Files\VST3` por padrão.
